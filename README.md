# tasks

Three-tier task tracker: an API, a background worker, a web frontend, Postgres,
Redis. Containerised, healthchecked, watched. The app is deliberately small —
this repo is mostly about how it gets built, shipped, and observed.

- **Live app**: <https://kamkait.ayoubabid.me/>
- **Live status**: <https://status.kamkait.ayoubabid.me/>

## Run it locally

Only requirement: **Docker** with the `compose` plugin.

```sh
git clone https://github.com/ClydeTN/kamka-tasks
cd kamka-tasks
cp .env.example .env          # set POSTGRES_PASSWORD to anything you like
docker compose up --build
```

Open <http://localhost:8080>. Five containers come up, each with its own
healthcheck:

| port | service |
|---|---|
| 8080 | `web` — nginx serving the React bundle |
| 4000 | `api` — express + drizzle |
| 5432 | `postgres` |
| 6379 | `redis` |
| —    | `worker` — BullMQ consumer (no port) |

The api runs its migrations on boot, so there's no manual DB step. To wipe the
database and start clean: `docker compose down -v`.

`compose.override.yaml` is auto-merged in dev and exposes each service's port
on the host so you can `psql`, `redis-cli`, or `curl` directly. Change the
host-side ports in `.env` if any of them are already taken.

## Run it without Docker

If you want hot-reload and your own Postgres/Redis:

```sh
# in three terminals
cd api    && npm install && npm run dev
cd worker && npm install && npm start
cd web    && npm install && npm run dev
```

Both `api` and `worker` need `DATABASE_URL` and `REDIS_URL` in their env. The
Vite dev server proxies `/api` to `localhost:4000` — see `web/vite.config.ts`.

## What gets persisted (volumes)

Compose declares named volumes so containers can come and go without losing
state. Only use `docker compose down -v` when you actually want a clean DB.

| volume | what's in it | rebuilt automatically? |
|---|---|---|
| `pgdata` | Postgres tables (`tasks`, `tags`, `comments`, `activity`, …) | no — back this up |
| `redisdata` | BullMQ queue + API list cache | yes |
| `caddy_data` | Let's Encrypt account + certs (prod only) | yes (re-issued) |
| `caddy_config` | Caddy runtime state (prod only) | yes |
| `uptime_data` | Uptime Kuma sqlite (prod only) | dump manually if you care |

On the deployed VM, a systemd timer runs `pg_dump` nightly into
`/opt/tasks/backups/` with 14-day retention. Locally, do what you'd do
anywhere: `docker compose exec postgres pg_dump -U tasks tasks > tasks.sql`.

## Project layout

```
api/        express + ts + drizzle. owns the schema and the BullMQ producer.
worker/     BullMQ consumer. one job type: due-reminders.
web/        vite + react + tailwind. served by nginx in production.
deploy/     what gets shipped to the VM: Caddyfile, deploy.sh, rollback.sh.
infra/      terraform: VM, firewall, IP, IAM. bootstrap.sh for one-shot WIF setup.
docs/       rollback-drill.md — evidence the rollback path actually works.
compose.yaml             local stack — builds locally, healthchecks, named volumes.
compose.override.yaml    dev-only host port mappings, auto-merged.
compose.prod.yaml        production stack — pulls from ghcr, adds Caddy + Uptime Kuma.
.github/workflows/       CI (path-filtered), terraform (manual apply), deploy.
```

## Secrets you'll need locally

Only one: `POSTGRES_PASSWORD` in `.env`. Any string. The local DB is
throwaway, so this value is meaningless beyond the api and postgres
container agreeing on it.

`.env` is gitignored. `.env.example` is the template — never put real
production secrets in it.

In prod, the postgres password is generated by Terraform and lives in two
places only: the TF state (private GCS bucket) and `/opt/tasks/.env` on the
VM (mode 0600). The deploy pipeline never sees it.

## Contributing

| branch | CI runs? | auto-deploys? |
|---|---|---|
| `main` | ✅ on push + PR | ✅ pushes deploy to prod |
| `develop` | ✅ on push + PR | ❌ never |
| feature branches | ✅ once a PR is opened | ❌ |

Branch off `develop`, open a PR back into `develop`. CI runs four jobs in
parallel (api, worker, web, terraform), each one gated by whether your diff
touched its directory — a docs-only PR finishes in seconds. When `develop`
is ready for a release, PR it into `main`; the merge auto-deploys.

`main` is the only branch with a path to production.

### What CI checks

- `api/`: `npm ci`, `tsc --noEmit`, `tsc` build
- `worker/`: `npm ci`, `node --check src/index.js`
- `web/`: `npm ci`, `tsc -b && vite build`
- `infra/`: `terraform fmt -check`, `terraform validate`

If your change doesn't touch any of those directories, none of these
jobs run.

## Health & observability

- Every container has a `HEALTHCHECK` (DB roundtrip for the api, heartbeat
  file for the worker, internal `/healthz` for the web).
- `docker compose ps` shows the health column.
- In production, Uptime Kuma at `status.kamkait.ayoubabid.me` polls the
  public endpoints every 60s — including a TLS-expiry monitor on the LE
  cert.

## Deploying / rollback / infra

`main` deploys itself — contributors don't run anything by hand. The
rollback path has been exercised end-to-end; evidence in
[`docs/rollback-drill.md`](docs/rollback-drill.md).
